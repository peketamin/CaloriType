## 1. 計算仕様

以下は合意内容を具体化する提案。端数・不明値・期間端の扱いを含め、実装前に確定する。

### 分量とPFC

基準量q0、基準カロリーE0、入力量qの場合：
- E = E0 × q / q0
- P・F・Cも同じ倍率で変更
- 分数操作は現在のEとPFCに1/nを掛ける
- ±操作では変更後E / 変更前EをPFCへ掛ける
- 例：400 → 1/2 → 200 → 1/2 → 100 kcal
- 表示の丸め結果を繰り返し計算へ戻さず、内部値を保持する

0 kcalからの加算や、PFCが不明な場合の比例計算は定義が必要。負の摂取量を保存しない。個数とグラムの換算には食品ごとの対応量が必要で、名前だけから換算しない。

PFCの割合はエネルギー比率で表示し、P×4、F×9、C×4を分母・分子に使う方針を採用。食品の表示カロリーとの不一致や不明値の表示詳細は未決定。

### 長期調整

完了日dの摂取量をI(d)、当日の目標をT(d)とする。期間内の完了日集合Cについて：

- 超過差分S = Σ[I(d) − T(d)]（d ∈ C）
- 今後の目標予算B = ΣT(d)（調整期限までの今後の日）
- 差分調整後の余地R = B − S
- 今後の日数Dが正なら1日あたりの目標への調整量A = −S / D
- 週単位表示はA × 7とし、実際の残り日数も併記する

例：今週300 kcal超過し、残り3日ならA = −100 kcal/日。残り予算と「目標へ足す・引く調整量」を別に表示する。

上位期間の調整では、その期間の開始から当日までの完了日の差分を1回だけ数える案とする。月・四半期のカードの差分をさらに足すと二重計上になるため、独立した集計から算出する。上位期間の開始からの差分を計算対象とする。

未記録・入力途中の日は摂取量も目標も差分へ含めない。履歴の不足を「余裕」と解釈せず、記録完了日数・未完了日数を併記する。

長期調整は翌日から期限までへ配分し、今日の残りはホームで別に計算する。残り0日の場合は差分のみ表示する。週表示は1日あたりの調整量×7とし、残り日数も併記する。上位期間の差分はその上位期間の開始から計算し、カード間の差分を重ねて足さない。将来の適用日ごとに目標予算を合計する。未設定の将来目標をどう継承するかは別途確定する。

## 2. データモデル

技術選定前の概念モデル。同期APIやDBスキーマの確定ではない。

| 概念 | 主な情報 |
| --- | --- |
| 食品・料理候補 | 安定ID、名前、基準量・単位、カロリー、PFC、出典・推定の区別 |
| 前回の入力 | 食品との関連、前回の量・単位・栄養値、補正情報、更新日時。過去の編集から学習するかは未決定 |
| 食事記録 | 安定ID、食品名と栄養値のスナップショット、量、実際の日時・タイムゾーン、所属日、ブロックID |
| 日次記録 | 所属日、終了境界、未記録/途中/完了の状態 |
| 食事ブロック設定 | 安定ID、表示名、色、順序 |
| 目標の版 | 適用開始日、入力条件、計算式の版、提案値、利用者が確定した目標 |
| バックアップ | スキーマ版、書き出し日時、記録・候補・設定・目標履歴 |

食品の基準値や前回値を更新しても、過去の食事は当時保存したスナップショットのままにする。変更・削除の版管理、同期用の削除情報、所有者IDは将来の同期設計で確定する。

## 3. 実装上の品質要件と設計案

### UIとチュートリアル

- Apple Human Interface Guidelinesを参考に、一貫した階層、読みやすい文字、十分な操作領域とフィードバックを備える。
- iOS標準アプリ相当の品質を目標とするが、Webをネイティブアプリと同一とみなさない。
- チュートリアルで検索・量の調整・移動・日付の区切り・取り消し・統計を段階的に紹介し、再表示できるようにする。
- タッチとキーボード操作、入力途中のフォーカス、IME変換確定を考慮する。
- ドラッグ以外の移動方法、色以外の超過表示、スクリーンリーダー対応を行う。

### 性能

要件は高速な入力と、データ蓄積後も遅くならないこと。候補表示100ms、保存反映200msを初期測定目標として、まず10万件で検証する。実測済みの保証ではない。性能を優先し、必要なら利用者と要件を調整する。対象端末・ブラウザ、p95などの指標、10万件を超える評価条件は継続検討する。

設計案：
- 日付・食品検索のインデックス、表示期間単位の読み込みを使う。
- 毎回全履歴を走査・書き換えず、集計を必要範囲だけ再計算する。
- 大量リストはページングや仮想化を検討する。
- IndexedDBを使い、日付・食品のインデックスと集計キャッシュを持つ。モデルの初期化や意味検索は入力経路から分離する。
- 少量・複数年・大量データで入力と集計の両方を検証する。

### セキュリティと将来の同期

- 初版の実記録は端末内保存。GitHubに保存するのはコードと設計文書であり、食事や身体情報ではない。
- 食品名など利用者入力を実行可能なHTMLとして扱わない。復元ファイルも信頼せず検証する。
- オンライン同期時は認証、所有者単位の認可、通信・保管時の暗号化、競合解決、削除の伝播、ログの個人情報除外を設計する。
- ローカル保存は端末紛失・ブラウザデータ削除からの保護ではない。バックアップ導線が必要。
- 初版は外部解析を導入しない。オフライン動作・インストール可能なPWA、端末側暗号化、同期サービスの保持期間は未決定。

## 4. 履歴・修復の詳細案

### 修復の設計案

通常起動に失敗する場合にも可能な範囲で診断画面を開く。先に読み取れる原本を退避・救出し、食品参照・日付・値・スキーマ・中断した移行を点検する。

再生成できるインデックス・検索用データ・集計は再構築する。解釈できない原本は黙って削除・書き換えず隔離し、結果と戻し方を示す。修復操作の自動適用範囲と確認手順は実装前に詰める。消失した原本を必ず復元できる保証はしない。

### 性能の設計案

履歴は全DBの1000コピーではなく、各操作で変更した対象の前後差分を基本にする。通常の表示では期間単位の読み出し、索引、増分集計、必要なら仮想化を使う。

件数に対して毎入力で全走査する処理を避ける。意味検索や修復は通常入力の100ms目標と分け、重い処理を分離する。

### 未決事項

履歴設定の範囲・容量、対象端末・ブラウザ・p95などの指標、10万件を超える評価、修復の検出・退避・隔離・復帰と移行方式。有限端末で無制限件数の一定時間を保証するものではない。性能のために利用者の記録を自動削除することは採用していない。


## 5. 食品データの更新案

初期データの配布版と本人の上書きを区別する。食品には安定IDを付け、初期データの更新で本人の編集を消さない。初期値へ戻す操作、インポート時の検証・プレビュー・退避を設計する。配布版との衝突と上書きの詳細は未確定。

## 6. モードと目標履歴

デモと記録はモード別の保存キーとセッション履歴を持つ。保存キューは書き込み時点のモードを捕捉し、切り替え後の状態を旧モードへ書かない。復元ファイルにmodeを含める。モードの分離はブラウザオリジン間の隔離ではない。

論理日付に適用する目標の版による集計が必要だが、現モックは現在の目標で比較している。[必要なルール](goal-changes.md)を確定してから実装する。

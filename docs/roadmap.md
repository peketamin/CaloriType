# CaloriType ロードマップ

更新日：2026-11-03  
関連：[デザインドック](design.md) / [ADR一覧](adr/README.md)

本書は優先順位と完成条件を示す。納期・工数の約束ではない。現在は要件定義段階で、以下のアプリ機能は未実装。

## フェーズ0：操作モックと仕様の確認

目的：全体像を見せ、手入力の速さと調整のわかりやすさを試す。

- ホーム、入力、タイムライン、ハンバーガーメニュー、統計の画面を用意する。
- 候補補完、量の調整、編集・削除、取り消し、ブロック移動をサンプルで操作できるようにする。
- 日付の区切り、カレンダー、天秤、期間別カード、チュートリアルを確認する。
- サンプルと実記録、推定値と確定値を区別する。
- 外食補正、前回値の記憶、日付境界の未決事項を確認する。

完成条件：代表的な記録と修正の流れを試し、入力のつまずきと計算上の未決事項を説明できること。画像だけでは操作モックの完成としない。

## フェーズ1：初版の記録・保全機能

目的：日々の入力、再利用、編集、復元を安心して使えるようにする。

- Webでの部分一致候補・自由入力、グラム・個数、カロリーとPFCの調整。
- 前回の料理の入力値の補完。材料を積み上げるレシピ機能は初版に含めない。
- 朝食・昼食・夕食・夜食と設定による変更、移動、日ごとの区切り。
- 合計と残量、食材換算、未記録・途中・完了の状態。
- 追加・編集・削除、元に戻す・やり直す。
- 端末内永続化、保存エラーの表示、JSON書き出し・復元、Markdown書き出し。
- 読みやすさ、キーボード・タッチ操作、再表示できるチュートリアル。
- データ量に応じた入力・表示性能の検証。

完成条件：デザインドックの記録・計算・保存・復元に関する受け入れ条件を満たし、通常の食事を短時間で記録し、翌日も継続して使えること。対象端末・件数・応答時間の数値は検証前に決める。

## フェーズ2：目標・統計を磨く

目的：入力した記録から、長期的な調整に使える情報を返す。

- 身体条件・活動量・体重目標・目標日からのカロリー提案と編集。
- 適用日を持つ目標履歴。
- 暦のカレンダー、色分けと週合計。
- カロリー超過に連動する天秤。
- 週・月・四半期・半年と上位期間の予算、日/週単位の調整量。
- 未完了日、計算対象日、目標と調整量の意味を明示する。

完成条件：未記録のゼロ扱い、差分の二重計上、目標変更による過去の評価の書き換えがなく、期限の端でも表示を説明できること。

この段階分けは統計を不要とするものではない。操作モックで先に全体を確認し、実用版では記録と保全を優先して統計を段階的に磨く。

## フェーズ3：オンライン同期

- 利用者認証と所有者ごとのアクセス制御。
- 安定ID、版、再送、競合、削除の伝播と複数端末。
- 通信・保管時の暗号化、バックアップ、復旧、保持期間、データ削除。
- 初版の端末データを移行できる方式。
- 運用・プライバシー・監視を含む独立した設計レビュー。

完成条件は同期設計時に確定する。端末内保存に同期を後付けする前提だけで、競合解決を省略しない。

## フェーズ4：iOSアプリ

- Webで検証した入力・計算・データ形式を基にiOSへ展開する。
- 技術スタック、コード共有範囲、配布方法、Webとの互換性をADRで決める。
- iOS標準の入力・アクセシビリティ・ライフサイクルに合わせて操作を調整する。

ネイティブ化と同期の実装順序は未決定。必要に応じて入れ替える。

## 初版で確約しないこと

- 食材を積み上げるレシピ管理、写真解析、バーコード読み取り。
- 運動ごとの自動カロリー加算。
- 体重変化の保証や天秤による減量予測。
- PWAのオフライン動作、サーバー同期、特定の技術スタック。
- 課金、広告、外部解析。

将来追加する場合は、目的・入力への影響・データ移行を明確にして範囲を更新する。

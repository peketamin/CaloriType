# 食品名からのオフラインPFC推測：技術調査と実装案

更新日：2026-11-03  
状態：調査・提案。自動推測の要件は採用、モデルと実装方式は未採用。モデルの学習・実行・性能試験はまだ行っていない。

## 結論

名前からPFCを自動補完する機能は、初期登録済みの食品データと前回値の検索から始められる。最初から独自モデルを学習する必要はない。

意味検索用の既存モデルを追加すると、表記の揺れや説明から近い食品を探せる。このモデルが出すのは食品候補との近さであり、実測された栄養値ではない。既知の食品の基準値と量からPFCを求め、推定の根拠を表示する。

「カレー」のように同名でも材料・分量が異なる料理は、名前だけで実際のPFCを一意に決められない。前回の本人の入力や補正を優先し、適切な候補がない場合は不明を保持して編集可能にする。

## 段階1：モデルなしの自動補完

- 頻出食品・料理を初期データとして同梱する。
- 表記・読み・別名を正規化して検索する。
- 一致する本人の登録/前回値 → 初期食品 → 類似候補の順で提示する案。
- 食品ID、基準量・単位、カロリー、PFC、出典、推定フラグを持つ。
- グラム・個数の量で比例変更し、本人が修正できる。
- 通常の検索・入力はネットワークやモデル初期化を待たない。

文部科学省は食品成分表のExcelを公開している。基礎食品の候補データとして調査する。料理1食分の標準値、個数の重量、別名は別途整備が必要であり、成分表だけで全て揃うとは扱わない。使用する版・正誤表・出典表記・利用条件を確認して取り込む。

## 段階2：軽量モデルで類似食品を検索

候補構成：
- バッチ準備：Python、Sentence Transformers。
- 既存の埋め込みモデル：intfloat/multilingual-e5-smallを比較候補にする。日本語の食品名での精度・モデル容量・ライセンス・速度を確認して採否を決める。
- 変換：ONNX。必要ならOptimumなどで変換し、量子化前後を評価する。
- ブラウザ：Transformers.js / ONNX Runtime Web。WASMで動く構成を基本候補にし、WebGPUは対応端末で評価する。
- 重い処理はWeb Workerへ分離。通常検索を先に返し、意味検索は非同期の補助候補として扱う。

### バッチで作るもの

1. 出典付きの食品データを正規化する。
2. 名前・別名・材料の特徴・調理法を検索用テキストにする。
3. 既存モデルでテキストをベクトルへ変換する。
4. ベクトルと食品IDの索引を保存する。
5. モデル・tokenizer・前処理・pooling・正規化・量子化の版を揃えてパッケージ化する。
6. 正解食品を人が確認した評価セットで、候補の正しさと基準量の取り違えを測る。

この処理は学習ではなく、既存モデルを使った索引の作成。食品を編集しただけでモデルの再学習は不要。名称や別名を変更した場合に対象の索引を更新する。PFCの数値だけを変えた場合は食品データを更新すればよい構成にする。

multilingual-e5-smallの場合はquery:/passage:の接頭辞、poolingと正規化をモデルの説明に合わせる。バッチ側とブラウザ側で同じ仕様を使い、変換・量子化で近さが変わる点も評価する。

### アプリで行うこと

1. 通常の名前検索・本人の記憶を即時に返す。
2. 必要な場合だけ入力文をベクトル化する。
3. 近い食品を複数提示し、選択した食品の基準値からPFCを補完する。
4. 類似度が足りない・食品の分類が違う場合は断定せず、候補か不明として扱う。
5. 手入力した値を遅れて到着した推論結果で上書きしない。
6. 個人の食品変更は端末内の索引に反映し、公開学習データへ自動送信しない。

近さの数値をそのまま正解確率として表示しない。油の有無、生/加熱後、皮付き/皮なし、単位・分量などの条件を文字検索と併用して区別する。

### オフラインで必要な準備

モデルだけでなくtokenizer、設定、実行用JS/WASM、食品データ、索引、必要なアプリ資産を端末へ配置・キャッシュする。初回取得前からオフラインで使えることは保証しない。

キャッシュが消えた場合や端末の容量不足・非対応の場合も、通常検索と手入力へ戻れるようにする。これはアプリ全体のPWAオフライン保証とは別の設計事項。

参考サイズの計算例：1万食品×384次元×4バイトのベクトルだけで約15.4 MB。モデル重み・tokenizer・検索索引は別途必要。smallという名称だけでiPhone向けに十分小さいとは判断しない。

## 独自モデルが必要になる場合

目的が「既知食品の検索」ではなく「未登録料理の栄養比率を出す」ことで、既存方式が評価上不足する場合に検討する。

必要なのは、料理名・材料や調理法などの説明と、同じ基準量に揃えた信頼できるPFCの教師データ。単なる名前の一覧だけでは足りない。

候補工程：
1. データの根拠と利用条件を確認し、量・単位を揃える。
2. 同じ料理の別名が学習と評価へ漏れないよう分割する。
3. 名前の埋め込みを入力にした小さな回帰モデル、または検索モデルの追加学習を比較する。
4. 値の誤差、未知の料理、過信、モデル容量、対象端末のp95遅延を評価する。
5. ONNXへ変換・量子化し、変換前後の結果を照合する。
6. モデルの版と推定根拠を記録し、失敗時に以前の方式へ戻せるようにする。

学習済みでも名前から材料・量が確定するわけではない。出力は推定として示す。利用者が修正した値を次回へ引き継ぐことを優先する。

## LLMとの比較

WebLLMのようにブラウザ上で生成モデルを実行する選択肢もある。WebLLMはWebGPU対応ブラウザが必要とされている。初期ダウンロード・メモリ・端末差、数値の根拠を評価する必要があるため、今回の高速入力の最初の方式としては、食品データ＋検索を先に検証する案とする。

## 未決事項

- 同梱する食品・料理の範囲、出典、再配布条件と更新。
- 既存の語彙検索で十分か、埋め込みモデルが必要か。
- 比較モデル、ONNX変換、量子化、配布容量、対象端末。
- 評価セット・指標・合格水準、類似候補を断定しない基準。
- 推論時のキャッシュ、個人データ編集後の索引更新、モデル更新の移行。
- 自動推測を初版のどこまで必須とするか。通常検索の性能目標と意味検索の目標は分ける。

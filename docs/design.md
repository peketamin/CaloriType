## 1. 目的と価値

食材・料理の一覧から標準値を選ぶだけでは、実際に食べた量との差を調整しにくい。CaloriTypeは手入力の速さ、候補補完、分量調整、前回の入力の再利用によって、自分の食事に合わせた記録を容易にする。

食品の栄養値には推定を含む。正確さを保証するのではなく、基準値を自分の量へ調整し、修正できることを価値とする。

- 主な利用場面は自炊。外食もモード切り替えとカロリーの上乗せ補正で支援する。
- 減量専用に限定せず、体重維持・筋力トレーニングでも共通の記録機能を使えるようにする。
- 最初はWeb。将来iOSアプリへ展開する。
- 名前はカロリタイプ / CaloriType。商標・ドメインの利用可否は未確認。ハッカージョークは名称検討時の希望であり、操作性より優先する要件ではない。

## 2. 合意済みの機能

### ホームと高速入力

1. 食材・料理名の一部を入力すると候補を表示する。
2. おおよそのカロリーを補完し、入力確定までは調整できる。
3. グラム・個数で量を入力できる。基準量と単位を表示する。
4. 自分の食品・料理を再利用できる。たとえばカレーは材料を積み上げる方式ではなく「1食分」として登録し、次回入力時に前回のカロリーを補完する。
5. 分数ボタンは1/8、1/5、1/4、1/3、1/2。現在値へ乗算し、連続操作も現在値を基準にする。
6. 増減ボタンは±10、±20、±50、±100、±200 kcal。
7. カロリーの変更にPFCを比例させ、割合も表示する。
8. 外食モードの切り替えスイッチと、補正率を10パーセントポイント刻みで増減するボタンを用意する。外食ラベルをメタデータとして保持する。
9. 頻出する一般的な食品・料理を初期登録する。利用者は画面から編集でき、食品データのエクスポート・インポートで上書きできる。
10. PFCは食材・料理名から自動推測・補完する。端末内の食品データを使う方式を基本案とし、未登録名に対するオフラインモデルの方式は調査・検証する。

入力はEnterで候補選択、量の調整後にEnterで保存。IME変換中は保存しない。候補は名前の一致を優先し、その中で最近使った食品を上へ表示する。スマホには保存ボタンも用意する。

前回確定した量・単位・カロリー・PFCをセットで補完し、基準量へ戻す操作を残す。入力中やキャンセルでは記憶を更新しない。過去記録の編集を前回値に反映する詳細は要確認。

PFC不明は0と区別し、個別編集できる。名前から自動推測した値は推定と表示し、根拠となる食品・基準量へ到達できるようにする。カロリーだけでも記録できる。表示はkcal整数、PFC小数1桁とし、内部精度は保持する。食品の初期データの出典・利用条件、0からの比例変更とモデル選定の詳細は継続検討。

外食補正は未補正値と別に管理し、切り替えや再利用で重複適用しない。例として補正率20%を30%にする操作は「+10%」であり、補正済み値へさらに1.1を掛ける意味ではない。PFCもカロリーと同じ倍率で変更する。初期の補正率と下限・上限は未決定。

食品マスターの上書きと、全記録を対象とするJSONバックアップ復元は区別する。食品の対応付けには安定IDを用い、食品変更で過去の食事のスナップショットは書き換えない。インポート形式と衝突ルールは実装時に詰める。

### タイムラインと日付

- 1日のタイムラインスケールを縦に表示し、食事ブロックを色分けする。
- デフォルトは朝食・昼食・夕食・夜食。設定から変更可能。
- 食べたアイテムをブロック間でドラッグ＆ドロップできる。
- 日付の区切りは原則24時。区切りバーをドラッグしてその日だけ変更できる。
- 例：11月3日の終了を翌2時に変更した場合、11月4日1時の食事は11月3日分に所属する。他の日の設定へ一括適用しない。
- 実際の日時と集計上の日付を区別する。隣接する日で二重計上・計上漏れを起こさない境界ルールは実装前に確定する。
- 毎日の合計と目標までの残量を表示する。残りカロリーをチョコレートの個数などに換算し、日によって換算食品を変える。

区切りのドラッグは当日20時〜翌6時、15分刻みにスナップする。隣接日の開始と前日の終了を一致させ、二重計上・空白期間を作らない。移動する食事を確定前に表示する。

タイムラインは時刻に比例させつつ、食事ブロックには読める最小高さを確保し、同時刻のアイテムをまとめる。ドラッグ以外に移動先選択を用意する。

ブロックは安定IDを持ち、名前・色・順序を編集できる。既存記録があるブロックはアーカイブ可能。削除する場合は記録の移動先を指定し、記録を連動削除しない。

タイムゾーンは初回設定を維持し、旅行時に過去の所属を自動変更しない。時差変更のUI、ブロック間移動での時刻変更、日をまたぐ移動の詳細は継続検討。

### ナビゲーション

- 左上にハンバーガーアイコンを置く。
- 押すと縦スクロール可能なメニューペインを開く。
- ホーム、統計、設定、書き出し・復元、チュートリアルへ到達できる設計とする。

### 統計・目標

- 統計の上半分はカレンダー。記録した日は摂取量に応じた背景色にする。
- 目標付近は薄い緑、過剰な摂取は赤系にし、量に応じて連続的に色を変える。未記録はゼロ摂取と区別する。
- カレンダーには週合計も表示する。
- 下半分は目標体重に関する視覚表現。天秤は摂取カロリーの超過で傾き、オーバーペースでは赤みを増す。実測体重の減少ペースや減量予測を表すものではない。
- スクロールすると週・月・3か月・半年の集計と調整余地を表示する。

| 表示期間 | 差分を調整する予算の範囲 | 表示する調整単位 |
| --- | --- | --- |
| 週 | その週の残り | 1日あたり |
| 月 | 所属する四半期の残り | 1週間あたり |
| 3か月 | 所属する半年の残り | 1週間あたり |
| 半年 | 所属する年の残り | 1週間あたり |

期間は暦の区切り：週は月〜日、四半期は1〜3月・4〜6月・7〜9月・10〜12月、半年は1〜6月・7〜12月、年は1〜12月。移動する過去30日などの期間は使わない。

### 目標カロリー

- 現在体重・目標体重・目標日と、身長・年齢・計算に必要な身体条件・活動量などを使い、カロリー目標を自動提案する。
- 提案された目標は利用者が編集できる。
- 初版では活動量を設定する方式を使い、個別の運動記録による予算の自動加算はしない。
- 目標変更は指定日以降へ適用し、過去の評価は当時の目標を使う。
- 計算式、必要な属性、活動係数、提案の適用範囲・上下限、達成不能な目標への対応は未決定。実装前に根拠とともにADRへ残す。
- 筋トレ用途のPFC目標設定と、実測体重の記録機能の範囲も未決定。

### 記録状態・CRUD・履歴

- 日ごとに未記録・入力途中・記録完了を区別する。
- 未記録を0 kcalとして扱わない。長期調整の差分計算には記録完了日を使う。
- 意図的に摂取ゼロの日は、未記録と区別して記録完了にできるようにする。
- 入力済みの食事は後から編集・削除できる。
- 元に戻す・やり直すボタンを用意し、削除も取り消せる。
- 完了後に食事を追加・編集・削除した場合は入力途中に戻し、再度完了すると長期差分へ反映する。
- 履歴はデフォルト1000操作、設定で変更可能。初版は現在の利用セッション内で保持する。
- 食事の追加・編集・削除・移動、日付境界、ブロック設定、目標設定を取り消し対象にする。新しい編集でやり直し履歴は破棄する。
- 再起動後の履歴保持は後続。復元は通常の操作履歴に混ぜず、復元前バックアップから戻せる方式を採る。

### 偉人の言葉のランダム表示（追加要望）

自分を律するきっかけとして、偉人の言葉の引用をランダムに表示できる機能を追加する。表示方針は以下を採用する。引用の文言・利用条件の確認と初版の必須完成条件に含めるかは未決定。

採用する表示方針：
- ホーム下部に「今日の言葉」を小さく表示し、1日に1つランダム選出して当日は固定する。
- 「別の言葉」で切り替えられ、設定で非表示にもできる。
- 食事入力を中断するモーダルや、カロリー超過を責める通知にはしない。
- 継続・習慣・節制に関する言葉を中心にする。
- 原典・著者・翻訳の出典と利用条件を確認した小規模な引用集を同梱する。
- 生成した文や出典不明の文を偉人の引用として表示しない。原文・訳文・要約は区別する。
- 表示には著者と出典への導線を付け、データには作品名・箇所・原典URL・訳者/翻訳出典・利用条件の確認状態を持たせる。
- 引用集の確認が済むまで、実際の引用文を収録済みとは扱わない。

詳細は[未決事項D20](open-decisions.md#d20)へ記録する。

### 保存・運用

- オンライン同期導入までは端末内に保存する。
- JSONとMarkdownへエクスポートできる。
- JSONは復元にも使える。
- 永続化はIndexedDBを採用する。安定ID、日付インデックス、スキーマ版を持つ。
- 全体バックアップのJSON復元は全体置き換え。事前検証、件数プレビュー、復元前バックアップを行い、失敗した復元を途中適用しない。
- 食品データだけの編集用エクスポート・上書きインポートも提供する。全体復元とは画面とファイル種別を分ける。
- マージ復元は後続。古いスキーマは対応版だけ移行し、未知の新しい版を勝手に解釈しない。
- 修復モードを設ける。診断、可能な範囲の救出、派生インデックス・集計の再構築、不正データの隔離を設計する。原本の退避を優先し、原本消失まで復旧できると保証しない。
- 保存失敗や容量不足を利用者が認識でき、誤って保存済みと表示しないことを設計上の受け入れ条件とする。
- プロトタイプのサンプル値と利用者の実記録を混同させない。

## 3. 計算仕様の初期案

以下は合意内容を具体化する提案。端数・不明値・期間端の扱いを含め、実装前に確定する。

### 分量とPFC

基準量q0、基準カロリーE0、入力量qの場合：
- E = E0 × q / q0
- P・F・Cも同じ倍率で変更
- 分数操作は現在のEとPFCに1/nを掛ける
- ±操作では変更後E / 変更前EをPFCへ掛ける
- 例：400 → 1/2 → 200 → 1/2 → 100 kcal
- 表示の丸め結果を繰り返し計算へ戻さず、内部値を保持する

0 kcalからの加算や、PFCが不明な場合の比例計算は定義が必要。負の摂取量を保存しない。個数とグラムの換算には食品ごとの対応量が必要で、名前だけから換算しない。

PFCの割合はエネルギー比率を想定し、P×4、F×9、C×4を分母・分子に使う案とする。これは実装提案であり、食品の表示カロリーとの不一致や不明値の表示ルールは未決定。

### 長期調整

完了日dの摂取量をI(d)、当日の目標をT(d)とする。期間内の完了日集合Cについて：

- 超過差分S = Σ[I(d) − T(d)]（d ∈ C）
- 今後の目標予算B = ΣT(d)（調整期限までの今後の日）
- 差分調整後の余地R = B − S
- 今後の日数Dが正なら1日あたりの目標への調整量A = −S / D
- 週単位表示ではA × 7を基本案とし、部分週の扱いを別途決定する

例：今週300 kcal超過し、残り3日ならA = −100 kcal/日。残り予算と「目標へ足す・引く調整量」を別に表示する。

上位期間の調整では、その期間の開始から当日までの完了日の差分を1回だけ数える案とする。月・四半期のカードの差分をさらに足すと二重計上になるため、独立した集計から算出する。上位期間の開始からの差分を計算対象とする。

未記録・入力途中の日は摂取量も目標も差分へ含めない。履歴の不足を「余裕」と解釈せず、記録完了日数・未完了日数を併記する。

長期調整は翌日から期限までへ配分し、今日の残りはホームで別に計算する。残り0日の場合は差分のみ表示する。週表示は1日あたりの調整量×7とし、残り日数も併記する。上位期間の差分はその上位期間の開始から計算し、カード間の差分を重ねて足さない。将来の適用日ごとに目標予算を合計する。未設定の将来目標をどう継承するかは別途確定する。

## 4. データ設計案

技術選定前の概念モデル。同期APIやDBスキーマの確定ではない。

| 概念 | 主な情報 |
| --- | --- |
| 食品・料理候補 | 安定ID、名前、基準量・単位、カロリー、PFC、出典・推定の区別 |
| 前回の入力 | 食品との関連、前回の量・値、補正情報、更新日時。保存粒度は未決定 |
| 食事記録 | 安定ID、食品名と栄養値のスナップショット、量、実際の日時・タイムゾーン、所属日、ブロックID |
| 日次記録 | 所属日、終了境界、未記録/途中/完了の状態 |
| 食事ブロック設定 | 安定ID、表示名、色、順序 |
| 目標の版 | 適用開始日、入力条件、計算式の版、提案値、利用者が確定した目標 |
| バックアップ | スキーマ版、書き出し日時、記録・候補・設定・目標履歴 |

提案：食品の基準値や前回値を更新しても、過去の食事は当時保存したスナップショットのままにする。変更・削除の版管理、同期用の削除情報、所有者IDは将来の同期設計で確定する。

## 5. UI・品質・セキュリティ

### UIとチュートリアル

- Apple Human Interface Guidelinesを参考に、一貫した階層、読みやすい文字、十分な操作領域とフィードバックを備える。
- iOS標準アプリ相当の品質を目標とするが、Webをネイティブアプリと同一とみなさない。
- チュートリアルで検索・量の調整・移動・日付の区切り・取り消し・統計を段階的に紹介し、再表示できるようにする。
- タッチとキーボード操作、入力途中のフォーカス、IME変換確定を考慮する。
- ドラッグ以外の移動方法、色以外の超過表示、スクリーンリーダー対応を設計案として追加する。

### 性能

要件は高速な入力と、データ蓄積後も遅くならないこと。候補表示100ms、保存反映200msを初期測定目標として、まず10万件で検証する。実測済みの保証ではない。性能を優先し、必要なら利用者と要件を調整する。対象端末・ブラウザ、p95などの指標、10万件を超える評価条件は継続検討する。

設計案：
- 日付・食品検索のインデックス、表示期間単位の読み込みを使う。
- 毎回全履歴を走査・書き換えず、集計を必要範囲だけ再計算する。
- 大量リストはページングや仮想化を検討する。
- IndexedDBを使い、日付・食品のインデックスと集計キャッシュを持つ。モデルの初期化や意味検索は入力経路から分離する。
- 少量・複数年・大量データで入力と集計の両方を検証する。

### セキュリティと将来の同期

- 初版の実記録は端末内保存。GitHubに保存するのはコードと設計文書であり、食事や身体情報ではない。
- 食品名など利用者入力を実行可能なHTMLとして扱わない。復元ファイルも信頼せず検証する。
- オンライン同期時は認証、所有者単位の認可、通信・保管時の暗号化、競合解決、削除の伝播、ログの個人情報除外を設計する。
- ローカル保存は端末紛失・ブラウザデータ削除からの保護ではない。バックアップ導線が必要。
- オフライン動作・インストール可能なPWA、解析の導入、端末側暗号化、同期サービスの保持期間は未決定。

## 6. 受け入れ条件

以下は検証用の条件案。計測値や詳細な境界仕様は別途確定する。

- 数文字の手入力から候補を選び、量を修正して確定できる。再利用時に前回値が補完される。
- 現在値400 kcalへ1/2を2回適用すると100 kcalとなり、PFCも1/4となる。
- ±の全候補で合計とPFCが更新され、負の値を保存しない。
- ブロック移動で同じアイテムを二重に作らず、その日の合計が変わらない。
- 翌2時の区切りで翌1時の食事が前日分に所属し、隣接日で二重計上されない。
- 未記録・途中・完了が区別され、未記録日が0 kcalとして長期差分に入らない。
- 過去の評価が、現在の目標変更で書き換わらない。
- 削除を元に戻せ、やり直しもできる。操作後の集計が記録と一致する。
- JSONの書き出し・復元で対応範囲のデータと設定が保たれる。不正なJSONで既存データを破壊しない。
- 保存失敗を表示できる。サンプルデータを実測値として見せない。
- 合意したデータ量と端末で応答時間目標を満たす。現段階では数値未確定。

## 7. 決定状況と残る具体化

初回20項目のおすすめは、2026-11-03の回答で追加・変更を含めて方針採用された。[決定状況と残る具体化](open-decisions.md)に項目別の採用内容と残件を記録する。

主な残件は、食品の配布データとライセンス、外食補正率の初期値・範囲、PFC推測モデルの選定と評価、自動目標の式、食品インポート形式、修復可能範囲、対象端末を含む性能条件。商標確認・ドメイン・同期/iOSの具体方式も未確定。

モデルを用いたPFC補完の技術調査は[オフラインPFC推測](offline-pfc.md)を参照。方式候補であり、モデル学習・同梱・性能検証の完了ではない。

## 8. 成功の見方

合意した価値検証は「いつもの食事を、量を調整して短時間で記録でき、翌日も続けられるか」。

入力完了までの時間、操作数、修正しやすさ、翌日の継続、復元の成功を検証候補とする。数値目標と計測方法は未決定。計測のために健康情報を外部送信することは合意していない。

## 1. Objective / Background — 目的と背景

既存の料理一覧で標準値を選ぶだけでは、実際に食べた量との差を調整しにくい。手入力、候補補完、量の調整、前回値の再利用で、自分の食事に合わせて短時間で記録できるようにする。

食品の栄養値には推定が含まれる。記録を調整しやすくすることを提供価値とし、実際の栄養値の正確さや体重変化を保証しない。

- 主な利用場面は自炊。外食はモードと割合補正で支援する。
- 減量・体重維持・筋力トレーニングに共通の記録機能を使える設計を目指す。
- 最初はWebで、将来iOSアプリへ展開する。
- 手入力の速さを最優先する。データ蓄積に伴う性能の問題には、方式・必要なら要件の調整で対応する。
- 名前はカロリタイプ / CaloriType。商標・ドメインの利用可否は未確認。

## 2. Users / Evidence / Assumptions — 利用者・根拠・仮説

### すでにわかっていること

利用者本人は、料理の標準値を選ぶだけでは自分の食べた量に合わず、量やカロリーを調整したいと述べている。料理は材料を積み上げず、1食分と前回値を再利用する形を希望している。本人以外へのインタビューや競合比較はまだ行っていない。

### 想定する利用者と場面

- 自炊した食事を、グラム・個数・前回値から調整して記録したい人。
- 外食も同じ記録の流れで概算・補正したい人。
- 日々の増減を、維持・減量・筋トレの目的に合わせて長期的に把握したい人。

### 未検証の仮説

- 候補を選んで量を直す方式は、既存の一覧入力や自由なメモより本人にとって速い。
- 前回値は入力の手間を減らし、量の変化にも無理なく修正できる。
- 記録完了を明示する負担より、未記録をゼロにしない価値が大きい。
- 同じ操作で維持・筋トレも満たせる。各用途で必要なPFC目標の違いは未検証。
- 日替わりの言葉は継続のきっかけになる。入力の邪魔にならないかは検証が必要。

検証案：まず本人が実際の食事を1週間記録し、初回・再入力・外食・編集・復元を観察する。公開前には本人以外の少人数にも試してもらう。人数・実施日程は未決定。

## 3. Success Metrics — 成功基準

技術的な応答速度と、人が記録し終わるまでの使いやすさは別に測る。外部解析は初版で導入せず、手動観察・端末内の検証用計測を基本案とする。

| 目的 | 指標・測り方 | 決定状況 |
| --- | --- | --- |
| 記録が速い | 食品名の入力開始から保存までの秒数・操作数。初回/再入力/外食を分けて観察 | 指標は採用、合格秒数は未決 |
| 翌日も続く | 試用期間中の記録継続日数・中断理由 | 期間・合格基準は未決 |
| 修正しやすい | 編集・移動・取り消しを説明なしで完了できるか | 合格率・対象者数は未決 |
| 保存を信頼できる | 正常バックアップの復元一致、保存・復元失敗時に既存データを保てるか | 機能要件は採用、検証データの範囲は未確定 |
| 待たされない | 候補表示100ms・保存反映200msを目標に、まず10万件で検証 | 数値目標は採用、端末・p95等は未確定 |
| 自動PFCが役立つ | 代表的な食品名で適切な候補・基準量が出る割合、手修正の頻度 | 評価セット・合格基準は未決 |
| 日替わりの言葉が役立つ | 継続の助けになったか、邪魔だったかを試用後に聞く | 評価案。採用時期・基準は未決 |

追加提案（未採用）：まず同じ食事を現在の記録方法とCaloriTypeで入力し、時間・誤操作・修正回数を比較して合格値を設定する。推測で一律の「何秒」を確定しない。

## 5. Requirements / User Interaction and Design — 機能・操作仕様

### デモと記録（試用）の切り替え

操作モックはデモモードとしていつでも試せる。デモと記録の保存先・履歴・復元対象を分け、デモのリセットで自分の記録を変更しない。初回はデモ、記録は食事・目標・体重が空から始まる。

GitHub Pagesの /CaloriType/ 配下へ公開する。コードの公開と本人の記録の公開は区別し、ブラウザ保存のデータをリポジトリへ自動送信しない。公開手順は[公開ガイド](../mockup/PUBLISHING.md)、実装上の不足は[仕様監査](spec-audit.md)を参照。

### ホームと高速入力

1. 食材・料理名の一部を入力すると候補を表示する。
2. おおよそのカロリーを補完し、入力確定までは調整できる。
3. グラム・個数で量を入力できる。基準量と単位を表示する。
4. 自分の食品・料理を再利用できる。たとえばカレーは材料を積み上げる方式ではなく「1食分」として登録し、次回入力時に前回のカロリーを補完する。
5. 分数ボタンは1/8、1/5、1/4、1/3、1/2。現在値へ乗算し、連続操作も現在値を基準にする。
6. 増減ボタンは±10、±20、±50、±100、±200 kcal。
7. カロリーの変更にPFCを比例させ、割合も表示する。
8. 外食モードの切り替えスイッチと、補正率を10パーセントポイント刻みで増減するボタンを用意する。外食ラベルをメタデータとして保持する。
9. 頻出する一般的な食品・料理を初期登録する。利用者は画面から編集でき、食品データのエクスポート・インポートで上書きできる。
10. PFCは食材・料理名から自動推測・補完する。端末内の食品データを使う方式を基本案とし、未登録名に対するオフラインモデルの方式は調査・検証する。

入力はEnterで候補選択、量の調整後にEnterで保存。IME変換中は保存しない。候補は名前の一致を優先し、その中で最近使った食品を上へ表示する。スマホには保存ボタンも用意する。

前回確定した量・単位・カロリー・PFCをセットで補完し、基準量へ戻す操作を残す。入力中やキャンセルでは記憶を更新しない。操作版では過去記録の編集確定も前回値へ反映する。食品マスターと過去記録の値は別に保持する。

PFC不明は0と区別する。カロリーが入力されPFCが不明な場合は、初期比率P15%・F25%・C60%で仮置きし、1本の直線上の2点スライダーで2.5ポイント刻みに調整できる。比率と推定のラベルを表示し、PFCを個別編集できる。名前から補完した値と、カロリーから比率で仮置きした値は区別して推定と表示し、根拠となる食品・基準量へ到達できるようにする。カロリーだけでも記録できる。表示はkcal整数、PFC小数1桁とし、内部精度は保持する。食品の初期データの出典・利用条件、0からの比例変更とモデル選定の詳細は継続検討。

外食補正は未補正値と別に管理し、切り替えや再利用で重複適用しない。例として補正率20%を30%にする操作は「+10%」であり、補正済み値へさらに1.1を掛ける意味ではない。PFCもカロリーと同じ倍率で変更する。初期の補正率と下限・上限は未決定。

食品マスターの上書きと、全記録を対象とするJSONバックアップ復元は区別する。食品の対応付けには安定IDを用い、食品変更で過去の食事のスナップショットは書き換えない。インポート形式と衝突ルールは実装時に詰める。

### タイムラインと日付

- 1日のタイムラインスケールを縦に表示し、食事ブロックを色分けする。
- デフォルトは朝食・昼食・夕食・夜食。設定から変更可能。
- 食べたアイテムをブロック間でドラッグ＆ドロップできる。
- 日付の区切りは原則24時。区切りバーをドラッグしてその日だけ変更できる。
- 例：11月3日の終了を翌2時に変更した場合、11月4日1時の食事は11月3日分に所属する。他の日の設定へ一括適用しない。
- 実際の日時と集計上の日付を区別する。隣接する日で二重計上・計上漏れを起こさない境界ルールは実装前に確定する。
- 毎日の合計と目標までの残量を表示する。残りカロリーをチョコレートの個数などに換算し、日によって換算食品を変える。

区切りのドラッグは当日20時〜翌6時、15分刻みにスナップする。隣接日の開始と前日の終了を一致させ、二重計上・空白期間を作らない。移動する食事を確定前に表示する。

タイムラインは時刻に比例させつつ、食事ブロックには読める最小高さを確保し、同時刻のアイテムをまとめる。ドラッグ以外に移動先選択を用意する。

ブロックは安定IDを持ち、名前・色・順序を編集できる。既存記録があるブロックはアーカイブ可能。削除する場合は記録の移動先を指定し、記録を連動削除しない。

タイムゾーンは初回設定を維持し、旅行時に過去の所属を自動変更しない。区分を選択・移動するとその範囲の開始時刻へ合わせる。初期範囲は朝食06:00〜11:00、昼食11:00〜17:00、夕食17:00〜21:00、夜食21:00〜翌06:00。開始時刻は設定から変更でき、次の区分の開始を終了とする。「現在時を指定」では現在の日時と対応する区分を選ぶ。日付境界のため開始時刻がその論理日に入らない場合は保存せず調整を案内する。時差変更のUIと旅行時の固定タイムゾーン実装は継続検討。

### ナビゲーション

- 左上にハンバーガーアイコンを置く。
- 押すと縦スクロール可能なメニューペインを開く。
- ホーム、統計、設定、書き出し・復元、チュートリアルへ到達できる設計とする。

### 統計・目標

- 統計の上半分はカレンダー。記録した日は摂取量に応じた背景色にする。
- 目標付近は薄い緑、過剰な摂取は赤系にし、量に応じて連続的に色を変える。未記録はゼロ摂取と区別する。
- カレンダーには週合計も表示する。
- 下半分は目標体重に関する視覚表現。天秤は摂取カロリーの超過で傾き、オーバーペースでは赤みを増す。実測体重の減少ペースや減量予測を表すものではない。
- スクロールすると週・月・3か月・半年の集計と調整余地を表示する。

| 表示期間 | 差分を調整する予算の範囲 | 表示する調整単位 |
| --- | --- | --- |
| 週 | その週の残り | 1日あたり |
| 月 | 所属する四半期の残り | 1週間あたり |
| 3か月 | 所属する半年の残り | 1週間あたり |
| 半年 | 所属する年の残り | 1週間あたり |

期間は暦の区切り：週は月〜日、四半期は1〜3月・4〜6月・7〜9月・10〜12月、半年は1〜6月・7〜12月、年は1〜12月。移動する過去30日などの期間は使わない。

### 目標カロリー

- 現在体重・目標体重・目標日と、身長・年齢・計算に必要な身体条件・活動量などを使い、カロリー目標を自動提案する。
- 提案された目標は利用者が編集できる。
- 初版では活動量を設定する方式を使い、個別の運動記録による予算の自動加算はしない。
- 目標変更は指定日以降へ適用し、過去の評価は当時の目標を使う。「変更後の予算を再計算」ボタンで差分を確認できる。初回は今日、通常の変更は翌日を初期値にする。今日からの場合はその日全体へ適用することを確認する。
- 身体条件からの自動提案の計算式、必須属性、活動係数、提案の適用範囲・上下限、達成不能な目標への対応は引き続き根拠を確認して具体化する。予算の再計算とは分ける。実装前に根拠と適用条件を技術設計へ記録する。
- 筋トレ用途のPFC目標設定と、実測体重の記録機能の範囲も未決定。

### 記録状態・CRUD・履歴

- 日ごとに未記録・入力途中・記録完了を区別する。
- 未記録を0 kcalとして扱わない。長期調整の差分計算には記録完了日を使う。
- 意図的に摂取ゼロの日は、未記録と区別して記録完了にできるようにする。
- 入力済みの食事は後から編集・削除できる。
- 元に戻す・やり直すボタンを用意し、削除も取り消せる。
- 完了後に食事を追加・編集・削除した場合は入力途中に戻し、再度完了すると長期差分へ反映する。
- 履歴はデフォルト1000操作、設定で変更可能。初版は現在の利用セッション内で保持する。
- 食事の追加・編集・削除・移動、日付境界、ブロック設定、目標設定を取り消し対象にする。新しい編集でやり直し履歴は破棄する。
- 操作履歴は状態全体のコピーではなく変更差分で保持する。再起動後の履歴保持は後続。復元は通常の操作履歴に混ぜず、復元前バックアップから戻せる方式を採る。

### 偉人の言葉のランダム表示（追加要望）

自分を律するきっかけとして、偉人の言葉の引用をランダムに表示できる機能を追加する。表示方針は以下を採用する。操作版は原典確認済みの3件と本アプリ訳を収録。配布用引用集の拡充・利用条件の確認と初版の必須完成条件に含めるかは継続検討。

採用する表示方針：
- ホーム下部に「今日の言葉」を小さく表示し、1日に1つランダム選出して当日は固定する。
- 「別の言葉」で切り替えられ、設定で非表示にもできる。
- 食事入力を中断するモーダルや、カロリー超過を責める通知にはしない。
- 継続・習慣・節制に関する言葉を中心にする。原文に英訳を併記し、訳者と翻訳の位置づけを表示する。現モックはCaloriTypeによる英訳。
- 原典・著者・翻訳の出典と利用条件を確認した小規模な引用集を同梱する。
- 生成した文や出典不明の文を偉人の引用として表示しない。原文・訳文・要約は区別する。
- 表示には著者と出典への導線を付け、データには作品名・箇所・原典URL・訳者/翻訳出典・利用条件の確認状態を持たせる。
- 引用集の確認が済むまで、実際の引用文を収録済みとは扱わない。

詳細は[未決事項D20](open-decisions.md#d20)へ記録する。

### 保存・運用

- オンライン同期導入までは端末内に保存する。
- JSONとMarkdownへエクスポートできる。
- JSONは復元にも使える。
- 永続化はIndexedDBを採用する。安定ID、日付インデックス、スキーマ版を持つ。
- 全体バックアップのJSON復元は全体置き換え。事前検証、件数プレビュー、復元前バックアップを行い、失敗した復元を途中適用しない。
- 食品データだけの編集用エクスポート・上書きインポートも提供する。全体復元とは画面とファイル種別を分ける。
- マージ復元は後続。古いスキーマは対応版だけ移行し、未知の新しい版を勝手に解釈しない。
- 通常の詳細集計は論理日付で直近2年のみ。古い原本は削除せず、年単位の派生キャッシュを持つ。年の途中の境界には集計済み範囲を持たせ、古い記録の編集時は該当年を無効化・再構築する。詳細は[2年窓と競合](data-window-and-conflicts.md)。
- タブ間の競合はレコード/設定項目単位で保存確定が後の変更を採用し、再描画・再計算とトーストで通知する。DB全体を後勝ちで上書きしない。
- 修復モードを設ける。診断、可能な範囲の救出、派生インデックス・集計の再構築、不正データの隔離を設計する。原本の退避を優先し、原本消失まで復旧できると保証しない。
- 保存失敗や容量不足を利用者が認識でき、誤って保存済みと表示しないことを設計上の受け入れ条件とする。
- プロトタイプのサンプル値と利用者の実記録を混同させない。

## 6. Non-functional Requirements — 品質

- Apple HIGを参考にした一貫した階層・可読性・十分な操作領域とフィードバックを備える。
- キーボード・タッチ・支援技術、文字拡大、IME、フォーカス復帰を確認する。色やドラッグだけに依存しない。
- 端末内保存の失敗を表示し、復元前の検証・退避と修復の導線を用意する。
- データが蓄積しても通常入力を軽く保つ。対象端末や実行条件ごとの性能予算を確定して検証する。
- 初版では実データを外部解析へ送らない。同期の認証・認可等は同期開始前に設計する。
- 初回のサンプルと本人の実記録を混同させない。操作版は初回デモ・空の記録モード・デモリセットを分離する。

計算式、スナップショット、履歴・修復、索引とキャッシュなどの具体化は[技術設計](technical-design.md)を参照。未採用のPFCモデル方式は[技術調査](offline-pfc.md)を参照。

## 7. Acceptance Criteria — 受け入れ条件

以下は検証用の条件案。計測値や詳細な境界仕様は別途確定する。

- 数文字の手入力から候補を選び、量を修正して確定できる。再利用時に前回値が補完される。
- 現在値400 kcalへ1/2を2回適用すると100 kcalとなり、PFCも1/4となる。
- ±の全候補で合計とPFCが更新され、負の値を保存しない。
- ブロック移動で同じアイテムを二重に作らず、その日の合計が変わらない。
- 翌2時の区切りで翌1時の食事が前日分に所属し、隣接日で二重計上されない。
- 未記録・途中・完了が区別され、未記録日が0 kcalとして長期差分に入らない。
- 過去の評価が、現在の目標変更で書き換わらない。
- 削除を元に戻せ、やり直しもできる。操作後の集計が記録と一致する。
- JSONの書き出し・復元で対応範囲のデータと設定が保たれる。不正なJSONで既存データを破壊しない。
- 保存失敗を表示できる。サンプルデータを実測値として見せない。
- 候補表示100ms・保存反映200msを目標に、まず10万件で検証する。対象端末・測定方法・統計指標は未確定。

追加して具体化する条件：
- 初期食品の編集・食品上書きインポートが、その食品を使った過去の記録を書き換えない。
- 外食率20%→「+10%」で30%となり、スイッチや再利用で複利・重複補正しない。
- 履歴1000操作の設定変更が機能し、容量不足を含む失敗時に保存済みと誤表示しない。
- 修復前に読み出せるデータを退避し、原本を保持したまま派生データを再構築できる。
- モデルが使えない環境でも通常検索と手入力が使え、手修正を遅延結果が上書きしない。
- 名言は出典確認済みの収録データだけから選ばれ、非表示にできる。

これらは機能の検証条件であり、第3節の利用価値の成功基準とは分ける。

## 8. Constraints / Dependencies / Risks — 制約・依存・リスク

| 項目 | 現状・依存 | 対応案と不足 |
| --- | --- | --- |
| 期間・予算・体制 | 開発に使える時間、目標日、費用上限は未指定 | 最初の試用開始日と費用上限を先に置く案 |
| 食品・引用のデータ | 配布可能な出典付きデータと引用集が必要 | 採用版・翻訳・利用条件・更新方法を確認する |
| 対応環境 | 最初はWebだが最低対応OS・ブラウザ・端末が未指定 | 実際に使うiPhoneとPCを最初の検証環境に指定する案 |
| 自動PFC | 適切な基準食品、量、必要ならモデルが必要 | 推定の表示、修正、通常検索へのフォールバック。精度基準を決める |
| データ保全 | ブラウザデータ削除や端末紛失で消失しうる | JSON、保存失敗表示、修復。バックアップ頻度は未決 |
| 記録完了 | 正確な長期差分と引き換えに、完了操作が増える | 完了忘れ・完了後の修正を試用で観察 |
| 入力・性能 | モデル・全履歴集計が入力を遅らせる可能性 | 処理を分離し、端末条件を含めて計測 |
| 公開・運用 | 商標、ドメイン、問い合わせ先、公開範囲が未確定 | 正式公開前に確認。実記録をリポジトリへ入れない |

## 9. Questions — 追加で必要なプロダクト判断

既存の機能詳細は[決定状況](open-decisions.md)に記録し、本節はこれまで明示していなかったプロダクト判断を扱う。以下のおすすめは未採用。

| ID | 足りないこと | おすすめ |
| --- | --- | --- |
| P01 | 最初に誰と何で価値を検証するか | まず本人が1週間使い、現在の方法と初回・再入力・外食の時間を比較する |
| P02 | 入力完了時間・継続の合格基準 | 本人の現在の入力時間を測ってから、短縮率と継続日数の基準を置く。100msの描画速度だけで成功としない |
| P03 | 最初の実用版を誰にどこまで公開するか | 本人だけの試用から開始し、保存・復元と中核入力を確認してから範囲を広げる |
| P04 | 自動目標・統計・名言・意味検索モデルをどこまで初回公開の必須とするか | 記録と保全を先行。語彙検索での自動PFCを基本に、他は段階追加する割付案を確認する |
| P05 | いつまで・いくらで・誰が完成を判断するか | 試用開始日、使える開発時間、費用上限、最終判断者を短く明示する |
| P06 | 初回開始と日々の運用の導線 | 目標の初期設定→最初の1件→翌日の再利用を確認し、サンプルの消去とバックアップ案内も含める |
| P07 | 利用者が困ったときの対応・公開後の更新 | 不具合連絡先、旧データ移行・バックアップの手順、更新失敗時の戻し方を公開前に用意する |

目標変更の適用日・履歴と自動提案の式は[目標変更の整理](goal-changes.md)にまとめる。合意済みの原則と、未採用の詳細提案を区別する。

## 10. Release / Validation — 試用と公開の進め方

未採用の計画案：
1. 操作モックで主要ストーリーと仮説を確認する。
2. 第7節の保存・復元・修正・日付の条件を満たしたWeb版で、本人が1週間試す。
3. 利用価値の測定結果と既知の問題を確認して、公開範囲と次の実装を判断する。
4. 食品・引用の利用条件、名称、対象環境、問い合わせ先とデータ保全の案内を確認して正式公開する。

実施日・対象者・責任者・合格閾値を指定するまでは、公開ゲートの完成とみなさない。モデルや名言の試用が、入力・保存の基本動作を止めない順序にする。

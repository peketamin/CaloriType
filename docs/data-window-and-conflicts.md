# 直近2年の集計と競合制御

更新日：2026-11-03  
状態：採用した仕様と実装。全端末・無制限件数の性能保証ではない。  
関連：[PRD](design.md) / [技術設計](technical-design.md) / [ADR-0012](adr/0012-record-level-last-commit-wins.md)

## 集計窓

通常のカレンダー・期間統計は論理日付で「今日から2年前」以降だけを対象にする。閏日が2年前に存在しない場合は月末へ合わせる。

2年より前の原本は削除しない。日付を指定すれば履歴として読むことができ、全体JSON/Markdownの書き出しには古い原本も含める。古い日付のカレンダーでは詳細数値を未記録と表示せず、「履歴」として原本へ導く。

年次集計は派生キャッシュであり、記録の正本ではない。初回移行・復元・修復では原本を年ごとに集計する。通常の入力ごとに全過去履歴を走査しない。

## 「年合計だけ」では不整合になる理由

今日が2026-11-03なら窓の開始は2024-11-03。2024年の中でも1月〜11月2日は年次キャッシュ、11月3日以降は詳細集計側になる。

2024年全体の合計を詳細側へ単純に足すと重複する。このため年次キャッシュに from / through を保持し、2024年の古い範囲は2024-01-01〜2024-11-02と明記する。境界が翌日に進む場合は境界年だけを更新する。

- 古い記録の追加・編集・削除：影響する年を無効化し、その年を再構築する。
- 日付所属の変更：移動元と移動先の年を対象にする。
- 古い適用日の目標を訂正する場合：影響する古い年だけ再構築する。
- 通常の未来の目標変更：過去の年次集計を変更しない。
- 明示的な0 kcal完了日も完了日数へ含める。
- 当時の目標がない日と、目標差分を算出できる日を区別する。
- PFC不明件数と比率から推定した件数もキャッシュで区別する。

古い原本を編集するときの年次再構築、全体書き出し、初回移行・修復は集計窓外を読む例外的なバッチ操作。これを完全禁止すると、保持した原本の訂正と年次キャッシュが一致しなくなる。

## 保存

IndexedDBのスキーマはv2：
- data：モードごとの設定・食品・目標履歴・完了状態・年次キャッシュ・単調増加の保存版。
- entries：キーは[mode,id]。モードと論理日付、および実日付の索引。
- 通常読込：直近2年と、必要なら閲覧中の古い1日分だけ。
- 通常保存：変更した記録・設定項目の差分だけ。
- 読み取りはメタデータと原本を同じreadonlyトランザクションで取得する。
- バックアップには原本と設定を含め、再生成できるキャッシュを正本にしない。

旧DBは検証してから移行し、不整合があれば原本を上書きせず停止する。移行・初回年次集計中は操作を一時的に無効にして読込中と表示する。

## タブ間の競合

「後勝ち」は端末の時計ではなく、IndexedDBトランザクションで保存が確定した順で決める。

- 同じ食事の同時編集：レコード単位で後の保存を採用する。
- 別の食事の編集：両方を保持する。
- 設定：変更された設定項目、食品ID、日付ごとの完了状態などを単位に適用する。
- 同じ適用日の目標：保存版を使って後の変更を選ぶ。
- 競合や別タブの更新を受け取ったら再描画・再計算し、トーストを出す。
- BroadcastChannelとstorageイベントを使う。これは将来のオンライン同期の競合解決そのものではない。
- 取り消しは新しい書き込みとして扱う。別タブの無関係な記録を丸ごと巻き戻さない。

保存失敗の差分は保持し、JSONの退避にも含め、次の保存で再試行する。保存できなかった変更を切り替え・再描画で黙って捨てない。全体JSON復元やデモのリセットは、通常の差分編集と違い、そのモード全体を明示的に置き換える操作とする。

## 確認した範囲と限界

クラウドLinux/Chromiumで、旧DB移行、過去の原本の保持、年途中の範囲表示、旧記録編集時の該当年再集計、別タブの同一記録/別記録、トースト、保存失敗の退避・再試行を検証する。

人工データ10万件の測定では、古い9.5万件を通常画面へ読み込まず、直近5000件だけを読んだ。初回年次キャッシュの生成には数秒かかる。継続的な性能は対象端末・件数・指標ごとに測定し、実機Safariや長期間の運用確認は別途必要。

ブラウザの容量は有限。無制限の保持容量や、失われた原本の復旧を保証するものではない。タイムゾーンの旅行時の固定、巨大な全体バックアップの分割/進捗表示は継続して具体化する。

測定記録（単発）：原本100,000件、通常読込5,000件。初回構築6,650ms、キャッシュあり読込32ms、候補反映1ms、保存と再描画74ms。再現は `npm run test:performance`。操作受け入れテストは `npm test`。
